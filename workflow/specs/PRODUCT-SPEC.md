# Product Specification

Status: approved v0.1, 12 October 2026. Owner: team. Approval by each role
owner and at least one teammate has been confirmed.

Sources: stakeholder decisions through 12 October 2026; binding group-planning
document; MP2 behavior at commit
9819b857d880134c1fc1ffef8a8bcd5d6e536f43. This document intentionally adapts
MP2 behavior to a deployed multi-user web application and PostgreSQL.

## Purpose and success

FacilityFlow AI gives Requesters, Technicians, and Facilities Managers one
traceable maintenance workflow. Each role has a separate simple web interface
and one bounded SoC LLM assistant. The core workflow remains fully usable when
AI is disabled, unavailable, rate-limited, or rejected.

The release succeeds when all three roles complete the lifecycle using separate
authorized views, representative forbidden actions are blocked server-side,
data survives restart/deployment, AI remains advisory, development and
production are separated, and every approved requirement has test evidence.

## Shared data

### Accounts

- Username: 3–32 characters; letters, digits, period, underscore and hyphen only;
  unique case-insensitively.
- Display name: 2–80 non-blank Unicode code points after trimming.
- Password: 8–24 Unicode code points; no composition rule; stored only as a
  maintained salted password hash.
- Role: exactly one of REQUESTER, TECHNICIAN, FACILITIES_MANAGER.
- Account records retain immutable ID, active state, timestamps and a session
  version used for invalidation.

### Requests

Each Request has an immutable internal ID and a unique immutable display ID
FF-000001 through FF-999999 generated by the database. Gaps are allowed; overflow
fails without creating a Request or Audit Event.

| Field | Rule |
| --- | --- |
| title | required; 5–100 Unicode code points after trimming |
| description | required; 10–2,000 code points |
| location | required; 2–120 code points |
| category | one active Category Catalogue value |
| reported urgency | Low, Normal, High, Emergency |
| manager priority | null before triage; then Low, Medium, High, Critical |
| assignment | null in OPEN; an active Technician in active work states |
| resolution summary | 10–2,000 code points when completing |
| transition/cancellation reason | 5–500 code points where required |

Internal line breaks and whitespace are preserved after outer trimming.
Supporting records are:

- Requester Update: 1–1,000 code points, author and time.
- Work Log: 1–1,000 code points, 1–1,440 whole minutes, author and time.
- Audit Event: immutable ID, UTC time, actor, action, target and safe structured
  details; never passwords or full free-text Request fields.

Initial categories are Electrical, Plumbing, HVAC, Structural, Cleaning, Safety,
and Other.

## Lifecycle

| State | Meaning | Assignment |
| --- | --- | --- |
| OPEN | submitted for triage | none |
| ASSIGNED | prioritized and assigned; work not started | active Technician |
| IN_PROGRESS | current Technician is working | active Technician |
| COMPLETED | submitted for Manager review | last Technician retained |
| CLOSED | Manager accepted the work | retained; normally read-only |
| CANCELLED | work must not continue | historical assignment may remain |

Only these transitions are valid:

| From | To | Actor/action | Conditions |
| --- | --- | --- | --- |
| none | OPEN | Requester creates | valid fields |
| none | OPEN | Manager records on behalf | existing Requester owner |
| OPEN | CANCELLED | owner cancels | reason |
| OPEN | ASSIGNED | Manager assigns | priority and active Technician |
| OPEN | CANCELLED | Manager cancels | reason |
| ASSIGNED | IN_PROGRESS | assigned Technician starts | same assignment |
| ASSIGNED | ASSIGNED | Manager reassigns | different active Technician, reason |
| ASSIGNED | CANCELLED | Manager cancels | reason |
| IN_PROGRESS | ASSIGNED | Manager reassigns | active Technician, reason |
| IN_PROGRESS | COMPLETED | assigned Technician completes | work log and resolution |
| IN_PROGRESS | CANCELLED | Manager cancels | reason |
| COMPLETED | CLOSED | Manager accepts | completion remains |
| COMPLETED | ASSIGNED | Manager returns | active Technician, reason |
| CLOSED | ASSIGNED | Manager reopens | active Technician, reason |

Every transition re-reads the persisted state, checks actor and object scope, and
commits the state change and one Audit Event atomically. Stale or repeated
commands fail without partial or duplicate writes. CLOSED and CANCELLED reject
ordinary edits and additions, except audited Manager corrections and the defined
CLOSED reopen operation.

## Shared functional requirements

- **REQ-SH-001:** The system shall support exactly the three defined roles and
  route an authenticated Account only to its role workspace.
- **REQ-SH-002:** Every protected read and write shall re-check the persisted
  Account active state and role; Requester ownership and Technician assignment
  shall also be checked server-side.
- **REQ-SH-003:** Authentication failure for an unknown username, wrong password,
  or inactive Account shall use the same message and reveal no account existence.
- **REQ-SH-004:** Logout, account deactivation, and Manager password reset shall
  invalidate affected sessions. Own-password and eligible role changes retain
  the current session, but the next request uses the persisted role. A Technician
  with ASSIGNED or IN_PROGRESS Requests cannot be deactivated until every active
  Request is reassigned or cancelled.
- **REQ-SH-005:** There is no inactivity timeout. Authentication uses a
  browser-session cookie that is Secure in HTTPS, HttpOnly, SameSite=Lax, and
  absent after browser-session end or explicit logout.
- **REQ-SH-006:** Every successful protected mutation shall identify actor and UTC
  time in an Audit Event. Audit login success, account creation/activation/
  deactivation/role/password changes, Request creation/edit/cancellation,
  priority/assignment, every lifecycle transition, Work Log creation and
  catalogue/skill migrations. Authorization failure shall change no business
  state and reveal no inaccessible record details. Failed login belongs only in
  a redacted operational log and shall not persist attempted passwords or unknown
  usernames as Audit Events.
- **REQ-SH-007:** Requests, Work Logs, Requester Updates and Audit Events shall not
  be hard-deleted through the UI; account deactivation preserves authorship.
- **REQ-SH-008:** Lists shall have deterministic order, case-insensitive trimmed
  search, visible filters, one-action reset and distinct empty/zero-result states.
- **REQ-SH-009:** Dates are stored in UTC and displayed with an unambiguous local
  date, time and zone. Inclusive local-date filters end before the next local day.
- **REQ-SH-010:** Forms shall label required inputs, associate specific errors
  with fields, preserve valid unsaved input on failure, prevent duplicate pending
  submission, and show the persisted result after success.
- **REQ-SH-011:** Destructive actions shall require confirmation; the destructive
  action is never the implicit default.
- **REQ-SH-012:** Role workspaces shall expose only role-relevant navigation.
  The authenticated header identifies role and username and provides main
  workspace, change password, about and logout. Hiding a link or control is never
  an authorization control.
- **REQ-SH-013:** Requester-visible history includes status events, reasons and
  Requester Updates but excludes Work Logs and private Manager data. Technician
  history includes assigned Request data, Requester Updates and Work Logs.
  Managers may view all history.
- **REQ-SH-014:** All multi-write business operations use one transaction and roll
  back completely on validation, concurrency, persistence or audit failure.
- **REQ-SH-015:** Development/demo initialization shall atomically seed
  requester1/2, technician1/2 and manager1/2 using documented development-only
  credentials plus representative Requests in all six states.
- **REQ-SH-016:** Production shall not seed demo data by default. An empty
  production database shall bootstrap one Manager from deployment secrets; demo
  seeding requires an explicit pre-initialization configuration flag.
- **REQ-SH-017:** No Account other than a Facilities Manager may create ordinary
  Accounts. The bootstrap and demo seed are the only exceptions.
- **REQ-SH-018:** AI is optional and advisory. An AI endpoint shall never call a
  business mutation, submit a Request, change priority, assign a Technician,
  transition state, append a Work Log, or close/cancel/reopen work.

## Quality requirements

- **NFR-SEC-001:** Use Spring Security server-side authorization, CSRF protection
  on state-changing browser requests, secure session cookies, prepared/parameter
  persistence operations, output encoding and restrictive security headers.
- **NFR-SEC-002:** Secrets exist only in approved local, GitHub, Vercel or database
  secret stores. They shall not appear in source, prompts, browser payloads,
  logs, Audit Events, screenshots, handoffs or test fixtures committed to Git.
- **NFR-PERF-001:** Under a documented 50-concurrent-user test, the p95 response
  time of non-AI application requests shall be at most one second, excluding
  client network latency. AI requests use their separate timeout contract.
- **NFR-A11Y-001:** Critical login and role workflows target WCAG 2.2 AA: keyboard
  operation, visible focus, programmatic labels, associated errors, no
  color-only meaning and at least 4.5:1 contrast for normal text.
- **NFR-A11Y-002:** Supported browser scope is the latest stable desktop Google
  Chrome at verification time. Pages remain usable from 760 × 600 upward and
  responsive at 1,024 × 700 and 1,440 × 900.
- **NFR-REL-001:** AI failure never blocks the corresponding manual workflow and
  never erases user-entered business data.
- **NFR-REL-002:** Production PostgreSQL is backed up at least daily with target
  RPO 24 hours and RTO 4 hours. One restore rehearsal is recorded before release.
- **NFR-OPS-001:** A non-sensitive health endpoint checks application and database.
  An external check runs every five minutes and alerts after three consecutive
  failures. Alert when HTTP 5xx exceeds 5% over five minutes where the free-tier
  monitoring stack supports it.
- **NFR-OPS-002:** Structured logs include correlation ID, time, severity,
  deployment version and safe event/error type, but exclude credentials, password
  material, raw AI prompts/outputs and full Request descriptions.
- **NFR-DEP-001:** Development/Preview and Production have separate PostgreSQL
  databases, secrets, SoCLaaS keys, configuration and hostnames. Production
  deployment requires an approved pull request and human promotion.
- **NFR-DOC-001:** User/Developer guides, MP2 reuse ledger, traceability, sanitized
  multi-agent handoffs and individual reflections remain current. Planned tests
  or controls are never described as executed.

These are design targets and acceptance criteria, not claims of current
verification.

## Out of scope

- email, SMS, push or calendar integration;
- maps, GPS, file/image attachments, inventory, invoicing or payments;
- custom roles or arbitrary workflow configuration;
- autonomous AI agents, tool calling, browsing, persistent AI chat or AI business
  actions;
- model training/fine-tuning or broad retrieval over user-supplied documents;
- native mobile clients and browsers outside the stated support target;
- advanced reporting or CSV export.

## Product acceptance

Release acceptance requires automated lifecycle, validation, authorization,
transaction and AI-failure tests; isolated PostgreSQL integration tests; focused
web/keyboard tests for critical workflows; a 50-user performance result; a
deployment/smoke/promotion record; backup-restore evidence; and a reviewed
traceability matrix. Specification approval does not claim implementation or
verification; those require the recorded evidence above.
